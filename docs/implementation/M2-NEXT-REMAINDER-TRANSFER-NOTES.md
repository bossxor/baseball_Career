# 시즌 중 타구단 계약 연결 인계 — 미구현 점검표

M2-CP는 비교 요청·고정 제안·원구단 재수락까지다. 이 문서는 다음 실제 타구단 수락의 구현 준비이며 기능 완료·새 사용자 승인·실행 검증으로 세지 않는다. 엔진만의 원자 결과를 먼저 완성하고 이후 DB revision CAS/command receipt에 연결한다.

## 사용자 확정과 기존 동작

- 계약 소진 뒤 다른 구단 제안을 비교하고, 새 계약 전에는 경기 진행을 보류한다.
- 새 계약 전에는 원구단 제안도 다시 수락할 수 있다.
- 타구단 연봉 환산액은 기존 선수 가치 산식, 실제 지급은 남은 등록 경기일 기준이다. 원구단의 기존 혼합 연봉 산식과 다르다. 14/21의 사용자 확정 U를 읽는다.
- CP 제안에는 정원/예산/남은 날짜 견적이 있다. 열람은 실제 예산 예약/지출·권리 이관·선수 이동이 아니다. 미래 수락은 제안 키/사건 버전/리비전/최신 재무를 재검사해야 한다.

## 현재 코드에서 그대로 이동시키면 깨지는 곳

1. `kbo-draft.ts`의 assertKboRecruitmentWorld는 구단별 현 계약 charge 합계가 paidSalaryWon+reservedSalaryWon과 같다고 검사한다. 원구단에서 소진 계약을 삭제하면 이미 지급한 돈의 귀속 근거가 없어진다. 새 구단의 원장으로 그 돈을 옮기거나 원구단 paid를 빼서 맞추지 않는다.
2. `kbo-remainder-pay.ts`의 v1은 previous.clubId===현재 clubId를 전제로 하며 priorPaidWon을 현재 계약 charge에 합산한다. 같은 구단 v1 값/원장/공개 결과는 유지하고, 타구단을 지원하는 명시 새 계약 버전 또는 동등한 귀속 구조가 필요하다. previous 원본 스냅샷은 수정하지 않는다.
3. `kbo-finance.ts`의 reserveKboOffseasonGuarantee, reserveKboPreseasonGuarantee, protectKboEmergencyBudget는 finance를 guarantees/grants 두 필드로 재조립한다. 귀속 원장을 새 필드로 추가한다면 이 세 writer와 다른 생성/연도 전환 경로가 이를 버리지 않게 해야 한다. 같은 시즌 보장/지원금과 지급 영수증을 중복 비용으로 세지 않는다.
4. `kbo-windows.ts`의 일반 팀경기 수는 현재 구단·현재 리그의 시즌 경기만 읽는다. 이적 때 이미 사용한 강화/스타일 키를 초기화하거나 새 구단이 입단 전 치른 경기를 내 등록 경기로 세지 않는다. `kbo-military-growth.ts`의 실제 등록 영수증 기반 계산을 참고하되 군 복무 프로그램이 없는 이적 선수에게 군 프로그램을 가짜로 만들지 않는다.
5. `kbo-season-growth.ts`의 일반 계획 경계는 현재 구단 경기 수로 날짜를 찾는다. 이전 구단에서 정한 계획도 실제 원래 날짜에 귀속되어야 한다. 같은 시즌 한 개 성장 예산·노쇠1회·이미 받은 성장/강화 불변이다. 복귀 컨디션6경기는 구단에 묶이지 않은 실제 건강 등록 근거를 계속 사용한다.
6. `kbo-callup.ts`의 20경기 평가도 현재 구단 경기 수를 사용한다. 이적 전 이력과 새 팀의 기용 검토 구간을 혼동하지 않게 기존 설계와 연결한다. 과거 E09/훈련/관계 사건을 삭제하지 않는다.

## 수락 결과에 함께 들어갈 것

한 복제본 안에서 제안/버전 검증 → 과거 원구단 지급 귀속 보존 → 새 잔여 계약/새 구단 예약 → 양 구단 명단·최소 합법 편성 → 보유권/등록·활성 소속 이관 → 성장/계획 등록 경계 → 기존 E30 및 경쟁 제안 종료 → 다음 날짜 재개를 처리한다. 중간 결과를 게시하지 않는다. 실패는 원본/급여/권리/RNG를 모두 보존한다.

원구단의 최소35명·1군28명·독립 퓨처스 합법 편성, 새 구단 최대60명/예산을 확인한다. 기존 repairKboDualLeagueRosters는 프리시즌 AI용이며 모든 팀 첫 명단을 다시 고르므로 그대로 시즌 중 호출하지 않는다. 필요하다면 대상 두 구단만 처리하는 명시 안전 경로를 만들고 무관한 팀/선수의 계약·기용을 바꾸지 않는 증거를 남긴다. 사용자 승인된 최소 충원 정책을 적용하며 임의 전원 리셋/방출은 금지한다.

새 팀 첫 등록의 동료1명 형성은 기존 사용자 결정이다. 고교/대학/이전 팀 관계를 보존하고 실제 등록 동료를 선택하는 기존 team-teammates/relation-notices 흐름을 재사용한다. 미래 계약·원구단 권리 이력·동시 활성 계약1개 조건도 함께 유지한다.

## 필요한 회귀 증거

- 비교 전/후 동일 세계, 원구단 수락 유지, 후보0개 안전 경로, 갱신된 예산/가짜 제안/구버전 거절.
- 다른 구단 수락 후 원구단 이미 지급액 불변, 새 구단 이전 지급액0, 다음 실제 등록일 새 연봉 일급1회. 재전송·JSON 복원·해당 날짜 재처리 모두 중복0.
- 두 구단의 선수 유일성·정원/1군/퓨처스 편성·권리와 등록 일치, 무관한 구단 불변. 슬롯/재무 실패 전부 롤백.
- 이적 전후 같은 시즌 강화/스타일1회·계획 날짜·연간 성장 상한·부상 잔여 경기·6경기 복귀 보정·구종XP 보존.
- 실제 정규 최종 날짜의 반올림 정산, 포스트시즌 추가 급여0, 다음 연도 원장/과거 기록 보존과 새 계약 개시.
- 새 저장은 옛 코드가 오해해 진행하지 못하도록 버전 경계를 명시한다. 기존 v1 같은 구단 계약과 KBO v1/v2/v3 읽기 증거를 남기고, 버전 숫자만 낮추는 롤백은 허용하지 않는다.

마일스톤 종료마다 전체 npm run check, 설계 패키지/359해시, STATUS 최상단 평가, PROGRESS/NEXT-SESSION/증거, 검증된 체크아웃→V: 해시 확인 후 커밋/push한다. V:/.git은 만들지 않는다.

## 준비 단계의 실제 위험 재현

[보조 점검](evidence/M2-CP-transfer-gap-probe.log)은 통제된 계약 소진 fixture를 복제해 소속/명단만 옮기는 잘못된 처리를 시도했다. 실제로는 원구단 급여 합계 검사보다 새 소속과 옛 복무 계약의 연결 검사(INVALID_KBO_SERVICE_PAYROLL)가 먼저 막았다. 독립적인 금액 계산에서도 원구단에 이미 지급한208,333원이 남는 것을 확인했다. 원본 세계/돈/계약은 불변이고 실제 이적을 게시하지 않았다.

초기 보조 스크립트는 급여 합계 오류만 예상해 assertion이 실패했다. [초기 로그](evidence/M2-CP-transfer-gap-probe-initial-failure.log)를 보존했고, 실제 선행 계약 검사와 금액 차액을 각각 확인하도록 점검만 수정했다. 실행 소스 변경은 없다. 이는 새 이적 명령의 성공 증거가 아니며, 핵심4개 회귀/전체 검사 통과 수에 더하지 않는다.
