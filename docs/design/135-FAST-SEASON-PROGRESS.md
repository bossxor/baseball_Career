# 135. 빠른 시즌 진행 — 성능 설계

2026-11-07. 근거: [14 커리어 진행 템포(사용자 확정)](14-CANONICAL-DECISIONS.md), SLB Career 관찰(시즌 1회 진행 약 8~15초, [벤치마킹 설계서](../benchmark/SLB_CAREER_IMPLEMENTATION_SPEC.md) SLB-03). 이 문서는 설계까지이며 구현은 별도 팀이 한다.

## 1. 목표와 불변 조건

| 구분 | 내용 |
| --- | --- |
| 체감 목표(U) | 버튼 한 번에 한 시즌. SLB 수준의 체감 속도 |
| 수치 목표(D, 측정 후 조정) | 데스크톱 기준 시즌 1회 진행 총 대기 15초 이내, 진행 화면에 월 단위 진척 표시. Android 기기 목표는 데스크톱 측정 후 정한다 |
| 바꾸지 않는 것 | 모든 공식 경기의 타석 단위 시뮬레이션과 공식 기록, 성장·건강·특성·구종 원장, 결정 사건에서의 정지, 결정적 재현(같은 seed·명령 → 같은 결과), JSON 재개, 저장 CAS |
| 하지 않는 것 | 타석·투구 개입(14), 기록 생략·샘플링으로 정확성 낮추기(아래 3단계는 사용자 승인 전 금지) |

## 2. 현재 구조(코드 확인)

- API: 시즌 진행 요청 1회에 최대 25초(`apps/api/src/span-budget.ts`, `PLAYBALL_SPAN_BUDGET_MS`), 넘으면 `BUDGET` 정지 후 같은 버튼으로 이어서 진행(`career-flow-screen.ts`).
- 엔진: 진행 호출당 최대 1,000타석·20이닝·7일(`kbo-progress.ts` `advanceKboCareer`, US·학교도 같은 패턴). 호출마다 career 검증(assert*), 상태 복제, 정지 사유 판정.
- 측정(2026-11-06, 공용 PC, 검증 도구 경로): 고교 시즌(리그 216경기) 단일 실행 약 227초, 대학 1년 약 6.5분([격차표](../implementation/M2-CLOSURE-GAPS-20261106.md)).
- 상태 크기: 대학 4년차 약 11MB, 그중 `previousSeasons`의 누적 health 중복 약 4.9MB([측정](../implementation/evidence/CLAUDE-20261107-state-size.md)). 큰 원문 봉인은 해시로 바꿈(00cf5db·29ded68).

## 3. 설계 — 단계별(앞 단계로 목표를 달성하면 다음 단계는 하지 않는다)

### 0단계: 측정(필수, 구현 전)
- 시즌 1회 진행을 실제 API 경로(HTTP → 엔진 → 저장)로 측정한다. 항목: 경기 시뮬레이션, 일 마감(성장·건강·특성·구종 정산), career 검증 함수, 상태 복제(`structuredClone`·spread), 봉인 해시, JSON 직렬화, DB 저장. 고교·대학·KBO·US 각 1시즌.
- 산출: 항목별 시간 비율 표와 상위 3개 병목. 이 표 없이 아래 최적화를 시작하지 않는다.

### 1단계: 정확성 손실 없는 최적화(팀 재량)
1. **검증을 경계에서 한 번만**: 같은 시즌 진행 요청 안에서 반복되는 career 전체 검증(assert*)과 봉인 재계산을 요청 시작·끝 1회로 모은다. 청크 사이에는 변경분만 검사한다. 저장 직전 전체 검증은 유지한다.
2. **복제 축소**: 청크마다 career 전체를 깊은 복제하지 않는다. 진행 루프 안에서는 하나의 작업 사본을 쓰고, 실패 시 원본을 그대로 반환하는 현재 원자성은 "요청 시작 시 1회 복제"로 보장한다.
3. **청크 상한 상향**: 요청 내부에서는 1,000타석·7일 상한 대신 정지 조건(결정 사건·시즌 끝·시간 예산)까지 연속 진행. 엔진 API의 기존 상한은 호환을 위해 유지하고 새 시즌 진행 함수에서만 넓힌다.
4. **저장 횟수**: 시즌 진행 1회 = 저장 1회(정지 시점). 중간 청크마다 저장하지 않는다. 시간 예산 초과 시에만 중간 저장(현재 BUDGET 구조 유지).
5. **상태 크기**: `previousSeasons`의 누적 health를 해당 시즌 행만 보관하도록 바꿔 직렬화 비용을 줄인다(구 저장 호환 읽기 유지).
6. **백그라운드 실행**: 브라우저·Android에서 시즌 진행을 요청 하나로 기다리지 않고, 서버 작업으로 돌리고 진척(월·경기 수)을 폴링 또는 스트리밍으로 받는다. 진행 화면은 SLB-03처럼 월 칩·진척 바(서버 값).

### 2단계: 계산 구조 개선(팀 재량, 결과 동일성 증명 필요)
- 같은 날 독립 경기의 병렬 처리(Worker). 날짜·경기 순서와 RNG 스트림 분리가 이미 결정적이면 결과 해시가 같아야 한다. 같지 않으면 채택하지 않는다.
- 핫 루프(타석 확률 계산·기록 누적)의 할당 줄이기.

### 3단계: 정확성 축소(사용자 승인 필요)
- 주인공이 출전하지 않는 NPC끼리의 경기를 타석 대신 경기 결과 단위로 계산하는 방식. 리그 통계·수상·라이벌·관계가 NPC 타석 기록을 쓰므로 영향이 크다. 1·2단계로 목표를 못 맞출 때만 영향 분석과 함께 결정 요청한다.

## 4. 화면

- 기본 CTA "이번 시즌 끝까지"(이미 있음). 진행 중 화면: 시즌·나이, 월 칩, 진척 바, 취소 없음. 결정 사건이면 그 자리에서 정지 카드.
- 중요 경기 중계 미리보기 기본 OFF(14). 켜면 해당 경기 직전에만 정지.
- 시간 예산 초과(BUDGET)는 사용자가 다시 누르지 않아도 이어지도록 6번 백그라운드 실행으로 대체한다.

## 5. 검수 기준

- 같은 저장·같은 명령으로 최적화 전후 시즌 결과 해시가 같다(1·2단계).
- 고교·대학·KBO·US 각 1시즌 데스크톱 측정표가 목표 이내, 측정 환경 기록.
- JSON 재개·CAS 충돌·실패 원자성 테스트 통과, 전체 `npm run check` 통과.
- 진행 중 앱을 닫았다가 열어도 같은 지점에서 이어진다(76 재개 규칙).
